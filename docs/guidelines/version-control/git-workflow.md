# Git 워크플로우

이 문서는 저장소의 브랜치 운영, PR, 병합, 히스토리 관리 규칙을 정의한다. 모든 기여자와 에이전트는 변경을 시작하기 전에 이 규칙을 읽고 따라야 한다. 브랜치 모델의 기반은 GitHub Flow다.

## 1. 브랜치 모델

GitHub Flow에서 `main`이 제품의 현재 상태이고, 모든 변경은 `main`에서 갈라진 짧은 수명 브랜치에서 이뤄진다.

- 규칙: `main`은 항상 배포 가능한 상태로 유지한다.
- 왜: `main`이 언제든 배포될 수 있어야 롤백과 배포 판단이 단순해진다. 깨진 `main`은 모든 작업의 출발점을 무너뜨린다.
- 좋은 예: `main`의 모든 커밋은 테스트를 통과한 상태로 병합된다.
- 나쁜 예: `main`에서 빌드가 깨진 채로 다음 수정을 기다린다.

- 규칙: 모든 작업은 `main`에서 생성한 짧은 수명 브랜치에서 한다.
- 왜: 변경 단위가 작고 범위가 명확해야 리뷰와 병합이 빨라진다. 오래 살아있는 브랜치는 충돌과 범위 확산을 불러온다.
- 좋은 예: `main`에서 `git switch -c feature/add-login-api`로 브랜치를 만들어 작업한다.
- 나쁜 예: 여러 기능을 한 브랜치에 담아 몇 주간 유지한다.

- 규칙: `main`에 직접 push하는 것을 금지한다.
- 왜: 리뷰를 거치지 않은 변경이 `main`에 들어오면 배포 가능 상태와 히스토리 신뢰성이 동시에 깨진다.
- 좋은 예: 작업 브랜치에서 PR을 열고 리뷰 승인 후 병합한다.
- 나쁜 예: `main`에서 커밋을 만들고 곧바로 push한다.

## 2. 브랜치 네이밍

- 규칙: 브랜치 이름은 작업 유형 접두사로 시작한다. 새 기능은 `feature/`, 버그 수정은 `fix/`, 문서 작업은 `docs/`, 잡무는 `chore/`를 쓴다.
- 왜: 이름만으로 브랜치 용도를 파악할 수 있어 조회와 리뷰 배정이 쉬워진다. 접두사가 없으면 이름이 작업 내용과 일치하는지 하나씩 열어 확인해야 한다.
- 좋은 예: `feature/add-login-api`, `fix/login-token-expiry`, `docs/update-git-workflow`, `chore/bump-node-version`
- 나쁜 예: `login-api`, `임시브랜치`, `2026-08-21-work`

- 규칙: 접두사 뒤의 설명은 kebab-case 소문자 영어로 쓴다.
- 왜: 대소문자와 공백 조합이 많아지면 같은 작업을 지칭하는 이름이 제각각이 된다. 형식을 하나로 고정하면 검색과 자동화 규칙이 단순해진다.
- 좋은 예: `feature/add-login-api`
- 나쁜 예: `feature/AddLoginAPI`, `feature/로그인-api`

## 3. PR 규칙

- 규칙: 모든 변경은 PR을 거쳐 `main`에 반영한다. 크기와 상관없이 예외 없다.
- 왜: PR은 리뷰의 장이자 변경 이력의 단위다. 우회 경로가 생기는 순간 리뷰 문화가 무너진다.
- 좋은 예: 한 줄 오타 수정도 브랜치를 만들어 PR로 제출한다.
- 나쁜 예: 사소한 변경이라며 `main`에 바로 커밋한다.

- 규칙: PR 설명에는 무엇을 바꿨는지, 왜 바꿨는지를 적는다.
- 왜: 리뷰어가 코드만 보고 의도를 추측하면 리뷰 품질이 떨어진다. 맥락이 설명에 있어야 코드는 코드 그대로 읽힌다.
- 좋은 예: "세션 만료 처리 로직을 수정함. 로그인 30분 후 토큰 갱신이 실패하는 문제 때문이다."
- 나쁜 예: "수정", "기타", 빈 설명

- 규칙: PR은 리뷰 가능한 크기로 작게 유지한다.
- 왜: 작은 PR은 리뷰가 빠르고 지적이 실제로 반영된다. 거대한 PR은 리뷰가 형식화된다.
- 좋은 예: 한 PR이 하나의 기능이나 하나의 수정만 다룬다.
- 나쁜 예: 기능 추가, 리팩터링, 설정 변경을 한 PR에 전부 담는다.

- 규칙: 병합 요청 전에는 셀프 리뷰를 한다.
- 왜: 스스로 diff를 다시 읽으면 명백한 실수를 남의 리뷰 전에 걸러낼 수 있다.
- 좋은 예: PR을 연 뒤 diff를 처음부터 훑고, 메모를 정리한 뒤 리뷰어를 지정한다.
- 나쁜 예: 커밋을 push하자마자 즉시 병합 요청한다.

## 4. 병합

- 규칙: 병합 방식은 squash merge를 기본으로 한다.
- 왜: PR 단위의 여러 커밋이 `main`에 한 커밋으로 남아 히스토리가 일관되고 읽기 쉬워진다. 리뷰 과정의 잔 커밋이 `main`을 오염시키지 않는다.
- 좋은 예: 리뷰 중 "wip", "fix typo" 커밋이 쌓인 PR을 squash merge로 한 커밋으로 병합한다.
- 나쁜 예: 작업 커밋이 전부 그대로 `main`에 흘러들어간다.

- 규칙: squash merge가 적합하지 않은 경우에만 다른 병합 방식을 쓰고, PR 설명에 그 사유를 적는다.
- 왜: 사유 없는 예외가 쌓이면 히스토리 일관성이 사라진다. 예외는 기록될 때만 관리된다.
- 좋은 예: "리뷰 단계별 진행 과정 보존을 위해 rebase merge로 병합함"이라고 PR 설명에 명시한다.
- 나쁜 예: 병합 방식을 그때그때 사유 없이 바꾼다.

## 5. .git 무결성

- 규칙: 공유된 브랜치의 히스토리 재작성을 금지한다.
- 왜: 이미 다른 기여자가 본 커밋을 다시 쓰면 각자의 로컬 히스토리가 어긋나고 복구 비용이 팀 전체에 생긴다.
- 좋은 예: 병합된 커밋을 되돌리려면 revert 커밋을 만든다.
- 나쁜 예: `main`의 과거 커밋을 고치려고 히스토리를 다시 쓴다.

- 규칙: 공유 브랜치에 `rebase -i`를 쓰는 것을 금지한다.
- 왜: 대화형 rebase는 커밋 해시를 바꿔버려 이미 공유된 히스토리와 충돌한다. 되돌림이 필요하면 revert로 새 커밋을 만든다.
- 좋은 예: 아직 push하지 않은 내 작업 브랜치에서만 `rebase -i`로 커밋을 정리한다.
- 나쁜 예: `main`이나 다른 사람이 작업 중인 브랜치에 `rebase -i`를 실행한다.

- 규칙: force push를 금지한다.
- 왜: 원격 히스토리를 로컬 상태로 덮어쓰면 다른 기여자의 커밋이 사라질 수 있다. 되돌림이 필요하면 revert를 쓴다.
- 좋은 예: 잘못 올린 커밋은 revert 커밋으로 되돌린다.
- 나쁜 예: `git push --force`로 원격 브랜치를 덮어쓴다.
