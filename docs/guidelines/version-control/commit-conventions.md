# 커밋 컨벤션

이 문서는 저장소의 커밋 메시지 작성 규칙을 정의한다. 모든 기여자와 에이전트는 커밋을 만들 때 이 규칙을 따른다. 커밋 형식의 기반은 Conventional Commits다. 규칙 강제는 문서 안내가 기본이며, 스택이 확정되면 도구로 검사하는 방향으로 발전시킬 수 있다.

## 1. 형식

- 규칙: 커밋 메시지 첫 줄은 `type(scope): subject` 형식으로 쓴다. scope는 생략할 수 있고, 필요할 때만 빈 줄 다음에 본문과 footer를 붙인다.
- 왜: 첫 줄에서 변경 종류와 범위, 내용이 한눈에 읽혀야 히스토리를 훑는 비용이 낮아진다. 본문과 footer는 첫 줄에 담기 어려운 맥락을 위한 자리다.

전체 구조는 다음과 같다.

```
type(scope): subject

본문(선택): 무엇을 왜 바꿨는지 상세히 적는다.

footer(선택): BREAKING CHANGE 같은 메타데이터를 적는다.
```

## 2. type 목록

- 규칙: type은 아래 9가지 중 하나만 쓰고 새 type을 임의로 추가하지 않는다.
- 왜: 목록이 열려 있으면 같은 성격의 변경이 제각각 표기되어 분류와 검색이 흐트러진다. 닫힌 목록일 때 통계와 자동화 규칙이 단순해진다.

| type | 설명 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 및 수정 |
| `style` | 동작을 바꾸지 않는 서식 정리(공백, 들여쓰기 등) |
| `refactor` | 동작 변화 없이 코드 구조 개선 |
| `test` | 테스트 추가 및 수정 |
| `chore` | 코드 본체 외 잡무(폴더 정리, 에셋 교체 등) |
| `build` | 빌드 시스템 및 의존성 변경 |
| `ci` | CI 구성과 스크립트 변경 |

## 3. subject 규칙

- 규칙: subject는 한국어로 쓸 수 있다. type과 scope는 Conventional Commits의 영어 키워드를 그대로 쓴다.
- 왜: 변경 내용을 모두가 쓰는 언어로 적어야 읽는 비용이 가장 낮다. 형식 키워드를 번역하면 도구가 메시지를 해석하지 못한다.

- 규칙: subject는 50자 이내를 권장한다.
- 왜: 길어진 첫 줄은 로그와 히스토리 뷰에서 잘리고, 핵심이 뒤로 밀려 스캔 효율이 떨어진다.

- 규칙: subject는 개조식 또는 명령형으로 쓴다.
- 왜: 조사와 서술어를 줄이면 무엇을 했는지가 더 또렷해진다. 커밋 제목은 완결된 문장이 아니라 표제에 가깝다.

- 규칙: subject 끝에는 마침표를 붙이지 않는다.
- 왜: 마침표는 길이만 늘리고 다른 규칙과 함께 지킬 때의 일관성을 해친다.

## 4. scope

- 규칙: scope는 선택이다. 변경이 특정 범위에 국한될 때 붙이고, 저장소 전반에 걸친 변경은 생략한다.
- 왜: 모든 커밋에 scope를 강제하면 어울리지 않는 값이 억지로 붙는다. 범위가 있을 때만 달아야 정보가 된다.

- 규칙: scope는 영어 소문자 kebab-case로 쓴다. 예: `guidelines`, `auth`.
- 왜: scope는 변경 범위를 검색 가능한 키워드로 남기는 역할이다. 표기가 섞이면 같은 범위가 여러 이름으로 흩어진다.

## 5. BREAKING CHANGE

- 규칙: 하위 호환성을 깨는 변경은 type 뒤에 `!`를 붙여 표시한다. 예: `feat!:` 또는 `feat(api)!:`.
- 왜: 호환성 깨짐은 리뷰와 배포에서 가장 먼저 걸러야 할 신호다. 첫 줄 표기가 고정되어야 스캔만으로 걸러낼 수 있다.

- 규칙: 깨짐의 상세는 footer에 `BREAKING CHANGE: <설명>`으로 적는다. `!`를 썼을 때도 footer 설명을 함께 남긴다.
- 왜: `!`는 깨짐의 존재만 알린다. 무엇이 어떻게 달라지는지는 설명이 있어야 사용자가 대응할 수 있다.

## 6. 좋은 예/나쁜 예

- 규칙: 커밋은 형식을 갖추고 무엇을 했는지 드러낸다.
- 왜: 형식과 구체성이 갖춰져야 히스토리 검색과 리뷰가 빨라진다.
- 좋은 예: `feat(guidelines): 지침 맵 추가`
- 나쁜 예: `수정함`

- 규칙: subject는 변경 내용을 특정할 수 있게 쓴다.
- 왜: 무엇을 바꿨는지 알 수 없는 커밋은 히스토리에서 정보를 주지 못한다.
- 좋은 예: `fix(auth): 세션 만료 후 토큰 갱신 실패 수정`
- 나쁜 예: `Update stuff`

- 규칙: type은 변경 성격에 맞게 고른다.
- 왜: type이 실제 내용과 어긋나면 히스토리 통계와 자동화를 믿을 수 없어진다.
- 좋은 예: `docs(guidelines): 커밋 컨벤션 문서 추가`
- 나쁜 예: `feat: 문서 오타 수정`
