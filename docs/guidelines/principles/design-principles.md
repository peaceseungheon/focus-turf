# 설계 원칙

이 문서는 이 저장소의 코드 작성과 리뷰에서 공통 기준으로 삼는 설계 원칙을 정의한다. 각 원칙은 규칙 한 줄, 왜 필요한지, 그리고 언어에 독립적인 의사코드 대응 예시로 구성하며 아직 기술 스택이 정해지지 않았으므로 특정 언어나 프레임워크를 가정하지 않는다.

## 단일 책임 (Single Responsibility Principle)

규칙: 모듈, 클래스, 함수는 변경해야 할 이유를 하나만 가진다.

왜: 변경 이유가 여러 개면 그중 하나의 수정이 나머지 이유들의 동작을 의도치 않게 깨뜨린다. 코드를 읽는 사람도 한 덩어리가 무엇을 책임지는지 한눈에 말할 수 있어야 한다.

좋은 예:

```
FUNCTION 주문총액계산(주문):
    총액 = 0
    FOR EACH 항목 IN 주문.항목목록:
        총액 = 총액 + 항목.단가 * 항목.수량
    RETURN 총액
```

나쁜 예:

```
FUNCTION 주문처리(주문):
    총액 계산
    재고 차감
    결제 승인 요청
    이메일 발송
    영수증 화면 문자열 조립
# 계산, 재고, 결제, 알림, 표현 중 무엇 하나를 바꿀 때마다 이 함수를 열어야 한다
```

## 개방-폐쇄 (Open-Closed Principle)

규칙: 확장에는 열려 있고 자기 코드 수정에는 닫혀 있게 만든다.

왜: 이미 동작하던 코드를 수정하면 검증된 부분이 깨질 위험이 따른다. 새 요구는 새 조각을 추가하는 방식으로 흡수하는 편이 안전하다.

좋은 예:

```
INTERFACE 결제수단
    FUNCTION 결제(금액)

FUNCTION 체크아웃(수단: 결제수단, 금액):
    RETURN 수단.결제(금액)
# 새 결제수단이 늘면 결제수단 구현을 하나 더 추가한다, 체크아웃 코드는 그대로다
```

나쁜 예:

```
FUNCTION 체크아웃(결제수단코드, 금액):
    IF 결제수단코드 == "CARD":
        카드 승인 절차
    ELSE IF 결제수단코드 == "BANK":
        계좌이체 절차
    ELSE IF 결제수단코드 == "KAKAOPAY":
        카카오페이 절차
# 수단이 하나 늘 때마다 이미 돌아가는 이 함수를 다시 편집해야 한다
```

## 리스코프 치환 (Liskov Substitution Principle)

규칙: 하위 타입은 상위 타입의 자리에 놓여도 계약을 깨지 않는다.

왜: 계약을 깨는 하위 타입이 섞이면 호출하는 쪽은 타입 검사 분기를 늘려 스스로를 지켜야 하고, 다형성의 이점이 사라진다.

좋은 예:

```
INTERFACE 재고저장소
    FUNCTION 조회(상품번호)
    FUNCTION 차감(상품번호, 수량)

FUNCTION 주문재고차감(저장소: 재고저장소, 주문):
    저장소.차감(주문.상품번호, 주문.수량)
# 메모리, 데이터베이스, 외부 API 어떤 구현을 넣어도 차감 계약은 동일하게 성립한다
```

나쁜 예:

```
예약전용저장소도 재고저장소 계약을 따른다고 선언
    FUNCTION 차감(상품번호, 수량):
        THROW "이 저장소는 차감을 지원하지 않는다"
# 차감이 항상 성공한다는 상위 계약의 가정이 무너지고 런타임에야 붕괴가 드러난다
```

## 인터페이스 분리 (Interface Segregation Principle)

규칙: 범용 인터페이스 하나보다 소비자가 쓰는 만큼만 담은 작은 인터페이스로 나눈다.

왜: 쓰지 않는 기능에 의존하면 그 기능이 바뀔 때 자신도 영향을 받는다. 인터페이스가 좁을수록 변경의 파급이 줄어든다.

좋은 예:

```
INTERFACE 인쇄기
    FUNCTION 인쇄(문서)

INTERFACE 스캐너
    FUNCTION 스캔(문서)

프린터 모듈은 인쇄기에만 의존하고 스캔 규격이 바뀌어도 알 일이 아니다
```

나쁜 예:

```
INTERFACE 복합사무기기
    FUNCTION 인쇄(문서)
    FUNCTION 스캔(문서)
    FUNCTION 팩스(문서)
    FUNCTION 소모품잔량조회()

인쇄만 하는 프린터 모듈도 팩스와 잔량조회까지 알고 구현해야 한다
```

## 의존성 역전 (Dependency Inversion Principle)

규칙: 상위 정책은 하위 사항의 구현이 아니라 추상화에 의존하게 만든다.

왜: 상위 로직이 구현 디테일을 직접 알면 디테일이 바뀔 때마다 상위 로직도 함께 흔들린다. 의존 방향을 역전시켜 안쪽이 바깥쪽을 모르게 만드는 편이 안정적이다.

좋은 예:

```
INTERFACE 알림채널
    FUNCTION 보내기(메시지)

FUNCTION 주문완료알림(채널: 알림채널, 주문):
    채널.보내기(주문.번호 + " 주문 완료")
# 주문 코드는 이메일인지 슬랙인지 모른다, 실행 시점에 채널이 주입된다
```

나쁜 예:

```
FUNCTION 주문완료알림(주문):
    클라이언트 = 새 슬랙클라이언트(토큰, 타임아웃, 재시도정책)
    클라이언트.메시지전송(주문.번호 + " 주문 완료")
# 알림 채널을 바꾸려면 주문 코드를 다시 편집해야 한다
```

## KISS (Keep It Simple, Stupid)

규칙: 같은 문제를 푸는 방법 중 가장 단순한 것을 택한다.

왜: 복잡함은 버그가 숨는 곳을 늘리고 읽는 사람의 시간을 먹는다. 단순한 해법이 실제로 부족해지는 지점이 올 때까지는 복잡하게 만들지 않는다.

좋은 예:

```
FUNCTION 최댓값찾기(숫자들):
    최댓값 = 숫자들의 첫 원소
    FOR EACH 숫자 IN 숫자들:
        IF 숫자 > 최댓값:
            최댓값 = 숫자
    RETURN 최댓값
```

나쁜 예:

```
FUNCTION 최댓값찾기(숫자들):
    정렬된목록 = 숫자들을 오름차순 정렬
    RETURN 정렬된목록의 마지막 원소
# 최댓값 하나를 얻으려고 전체 정렬 비용을 지불한다
```

## YAGNI (You Aren't Gonna Need It)

규칙: 지금 요구에 없는 기능은 미리 만들지 않는다.

왜: 미래를 위한 코드는 대개 예상한 형태 그대로 쓰이지 않고, 유지 비용과 테스트 부담만 먼저 발생한다. 필요해질 때 그때 만든다.

좋은 예:

```
FUNCTION 금액합계(항목들):
    합 = 0
    FOR EACH 항목 IN 항목들:
        합 = 합 + 항목.원화금액
    RETURN 합
```

나쁜 예:

```
FUNCTION 금액합계(항목들, 통화목록, 환율테이블, 반올림정책):
    IF 항목들에 통화가 섞여 있으면 환율테이블로 원화로 변환
    IF 반올림정책이 은행가 방식이면 규칙 A를 적용, 아니면 규칙 B를 적용
    ...
# 지금 요구는 원화 합계 하나뿐인데 오지 않은 미래를 위한 분기만 늘었다
```

## DRY (Don't Repeat Yourself)

규칙: 같은 지식은 한 곳에서만 정의한다.

왜: 같은 지식이 여러 곳에 흩어지면 한 곳만 바뀌어 서로 어긋나는 순간 그 자체가 버그가 된다.

주의: 과도한 추상화는 금지다. 우연히 닮은 코드 두 조각이 반드시 같은 지식은 아니다. 두 코드가 같은 지식을 표현하고 함께 변할 때만 합치고, 그렇지 않다면 중복을 남기는 편이 낫다. 잘못된 추상화는 중복보다 되돌리기 어렵다.

좋은 예:

```
부가세율 = 0.1

FUNCTION 부가세계산(공급가액):
    RETURN 공급가액 * 부가세율
```

나쁜 예:

```
주문 모듈: 세금 = 가격 * 0.1
정산 모듈: 세금 = 가격 * 0.10
환불 모듈: 세금 = 가격 * 0.1
# 세율이 바뀌면 세 곳을 찾아다 고쳐야 하고 하나라도 빠지면 어긋난다
```

## 높은 응집도와 낮은 결합도 (High Cohesion, Low Coupling)

규칙: 함께 바뀌는 것은 함께 묶고, 서로 무관한 것은 서로 모르게 만든다.

왜: 관련 코드가 흩어지면 하나의 변경이 여러 곳을 오가야 하고, 무관한 코드가 얽히면 한쪽 변경이 예고 없이 다른 쪽으로 번진다.

좋은 예:

```
재고 모듈 안에 입고, 출고, 재고조회가 함께 있고 재고 데이터는 모듈 밖으로 새지 않는다
주문 모듈은 재고 모듈이 공개한 조회 규격만 호출한다
```

나쁜 예:

```
주문, 배송, 리포트 모듈이 각자 재고 데이터를 직접 읽고 고친다
재고 규칙이 바뀌면 어느 모듈이 데이터를 건드렸는지 전부 뒤져야 한다
```

## 관심사 분리 (Separation of Concerns)

규칙: 비즈니스 규칙, 입출력, 표현 같은 서로 다른 관심사를 서로 다른 부분으로 나눈다.

왜: 관심사가 뒤섞이면 규칙 하나를 바꾸는 일도 저장과 화면 코드를 함께 건드려야 하고, 검증도 어려워진다.

좋은 예:

```
FUNCTION 주문총액계산(주문)
    총액 계산만 수행, 파일이나 네트워크 입출력 없음

FUNCTION 주문저장(주문)
    저장소 입출력만 수행

FUNCTION 영수증화면그리기(주문)
    화면 표현만 수행
```

나쁜 예:

```
FUNCTION 주문화면그리기(주문):
    할인 규칙 계산
    결제 승인 요청
    저장소에 저장
    화면 문자열 조립
# 규칙, 결제, 저장, 표현이 한 몸통에 뒤섞여 어느 하나만 바꾸기 어렵다
```

## 가독성 우선 (Readability First)

규칙: 영리한 코드보다 읽기 쉬운 코드를 택한다.

왜: 코드는 쓰이는 횟수보다 읽히는 횟수가 훨씬 많다. 잠깐의 작성자 자랑은 이후 모든 독자에게 세금으로 남는다.

좋은 예:

```
FUNCTION 결제금액계산(주문, 회원):
    할인대상금액 = 주문.총액 - 주문.배송비
    할인액 = 할인대상금액 * 회원.등급할인율
    RETURN 주문.총액 - 할인액
```

나쁜 예:

```
FUNCTION 결제금액계산(주문, 회원):
    RETURN 주문.총액 - ((주문.총액 - 주문.배송비) * IF 회원.등급 == "VIP" THEN 0.1 ELSE IF 회원.등급 == "GOLD" THEN 0.05 ELSE 0)
# 조건 셋을 한 줄에 눌러 담아 읽는 사람이 머릿속으로 다시 풀어야 한다
```

## fail fast (조기 실패)

규칙: 문제를 감지한 즉시 실패하고 조용히 넘기지 않는다.

왜: 오류는 발생 지점에서 진단하기 가장 싸다. 잘못된 값이 흘러간 뒤의 실패는 원인 추적 비용이 몇 배로 붙는다.

좋은 예:

```
FUNCTION 이체실행(계좌, 금액):
    IF 금액 <= 0:
        THROW "이체 금액은 0보다 커야 한다"
    IF 계좌.잔액 < 금액:
        THROW "잔액이 부족하다"
    계좌.잔액 = 계좌.잔액 - 금액
```

나쁜 예:

```
FUNCTION 이체실행(계좌, 금액):
    IF 금액 <= 0:
        금액 = 1
    IF 계좌.잔액 < 금액:
        금액 = 계좌.잔액
    계좌.잔액 = 계좌.잔액 - 금액
# 실패를 삼켜 잘못된 결과가 조용히 아래로 흘러간다
```

## 불변성 선호 (Prefer Immutability)

규칙: 값은 만든 뒤 바꾸지 않고, 변경이 필요하면 새 값을 만들어 반환한다.

왜: 불변 값은 공유해도 안전하고 누가 언제 바꿨는지 추적할 필요가 없다. 가변 상태를 여러 곳이 공유하면 재현 어려운 버그의 주 원인이 된다.

좋은 예:

```
FUNCTION 할인적용(주문, 할인액):
    새주문 = 주문을 복사
    새주문.총액 = 주문.총액 - 할인액
    RETURN 새주문
```

나쁜 예:

```
FUNCTION 할인적용(주문, 할인액):
    주문.총액 = 주문.총액 - 할인액
# 같은 주문을 참조하던 다른 코드가 예고 없이 다른 값을 보게 된다
```
