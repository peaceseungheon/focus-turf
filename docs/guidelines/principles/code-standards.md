# 코드 표준

이 문서는 이 저장소의 모든 코드에 공통으로 적용되는 표준을 정의한다. 각 규칙은 한 줄 선언, 왜, 좋은 예와 나쁜 예로 구성하며, 코드 예시는 특정 언어에 묶이지 않는 의사코드로만 표현한다.

## 네이밍

이 절의 규칙은 모든 언어에 공통으로 적용한다. camelCase, snake_case 같은 언어별 표기 관행은 이 문서가 정하지 않고 스택 확정 후 [../stack/README.md](../stack/README.md)가 정한다.

### 이름만 읽어도 의도가 드러난다

왜: 이름은 코드에서 가장 값싼 문서다. 이름이 의도를 말하지 않으면 모든 독자가 정의로 거슬러 올라가 뜻을 다시 짜맞춰야 한다.

좋은 예:

```
활성회원목록 = 활성회원전체조회()
경과일수 = 오늘 - 주문.주문일
```

나쁜 예:

```
data = 불러오기()
tmp = 오늘 - 주문.주문일
# data가 무엇을 담았는지, tmp가 어디서 왔는지 이름이 아무 말도 하지 않는다
```

### 매직 넘버를 쓰지 않고 이름 있는 상수로 표현한다

왜: 숫자 리터럴은 왜 그 값인지 스스로 설명하지 못한다. 상수 이름은 의도를 드러내고, 값이 바뀔 때도 한 곳만 고치면 되게 한다.

좋은 예:

```
최대주문수량 = 100

IF 주문.수량 > 최대주문수량:
    THROW "주문 수량이 상한을 넘었다"
```

나쁜 예:

```
IF 주문.수량 > 100:
    THROW "주문 수량이 상한을 넘었다"
# 100이 정책 상한인지 임시값인지 시스템 제한인지 코드가 말하지 않는다
```

## 함수

### 한 함수는 한 가지 일만 한다

왜: 일이 둘 이상이면 함수 이름은 일의 전부를 대표하지 못하고 수정 이유도 여러 개가 되어 변경이 예고 없이 번진다. 하는 일을 한 문장으로 요약하지 못하면 쪼갠다.

좋은 예:

```
FUNCTION 주문확인메일본문조립(주문):
    본문 = 주문.번호 + " 주문이 확정되었다"
    RETURN 본문 + 배송안내문구(주문.배송지역)
```

나쁜 예:

```
FUNCTION 주문완료처리(주문):
    메일 본문 조립
    메일 서버에 발송 요청
    발송 이력 저장
    실패하면 3회 재시도
# 조립, 발송, 기록, 재시도 정책이 한 몸통에 뭉쳐 있다
```

### 매개변수는 최소로 유지한다

왜: 매개변수가 늘수록 호출부가 기억할 것이 늘고, 비슷한 값의 순서를 바꿔 끼우는 실수도 눈에 띄지 않는다.

좋은 예:

```
FUNCTION 배송비계산(주문):
    RETURN 지역기준요금(주문.배송지역, 주문.총무게)
```

나쁜 예:

```
FUNCTION 배송비계산(지역, 무게, 회원등급, 쿠폰번호, 주문번호, 접수채널):
    ...
# 무엇이 필수이고 무엇을 비워 둘 수 있는지 호출부가 전부 기억해야 한다
```

### 조기 반환으로 정상 흐름을 한눈에 보인다

왜: 예외 조건이 본문을 감싸면 읽는 사람이 매 단계마다 지금 어떤 경우인지 머릿속으로 추적해야 한다. 조기 반환으로 걸러 내면 본문에 정상 흐름만 남는다.

좋은 예:

```
FUNCTION 회원할인액계산(회원, 주문):
    IF 회원이 아니면:
        RETURN 0
    IF 주문.총액 == 0:
        RETURN 0
    RETURN 주문.총액 * 회원.등급할인율
```

나쁜 예:

```
FUNCTION 회원할인액계산(회원, 주문):
    IF 회원이면:
        IF 주문.총액이 0이 아니면:
            RETURN 주문.총액 * 회원.등급할인율
        ELSE:
            RETURN 0
    ELSE:
        RETURN 0
# 정상 계산 한 줄을 읽으려면 조건 두 겹을 들여다봐야 한다
```

### 깊은 중첩을 만들지 않는다

왜: 들여쓰기가 한 겹씩 깊어질수록 독자가 함께 들고 가야 할 조건 문맥이 하나씩 늘어난다. 조기 반환, 흐름 건너뛰기, 함수 추출로 겹을 줄인다.

좋은 예:

```
FUNCTION 품절상품목록조회(상품들):
    품절목록 = 빈 목록
    FOR EACH 상품 IN 상품들:
        IF 상품.재고 > 0:
            CONTINUE
        품절목록에 상품 추가
    RETURN 품절목록
```

나쁜 예:

```
FUNCTION 품절상품목록조회(상품들):
    품절목록 = 빈 목록
    FOR EACH 상품 IN 상품들:
        IF 상품.재고 == 0:
            IF 상품이 숨김 처리되지 않았으면:
                IF 상품.판매중지일이 없으면:
                    품절목록에 상품 추가
    RETURN 품절목록
# 조건 세 겹 안쪽의 추가 문장 하나를 확인하려면 바깥 조건 셋을 다 기억해야 한다
```

## 주석

### 주석은 무엇이 아니라 왜를 설명한다

왜: 코드가 하는 일은 코드가 이미 말한다. 무엇을 되뇌는 주석은 코드가 바뀌는 순간 어긋나서 오히려 잘못된 정보가 된다.

좋은 예:

```
# 은행 마감(23시) 이전 입금만 당일 정산에 반영된다
IF 입금시각 < 은행마감시각:
    당일정산에 포함(입금)
```

나쁜 예:

```
# 입금시각이 마감시각보다 작으면 당일 정산에 포함시킨다
IF 입금시각 < 은행마감시각:
    당일정산에 포함(입금)
# 코드를 소리 내어 다시 읽어 주는 주석은 근거를 더하지 않는다
```

### 주석 처리된 죽은 코드를 남기지 않는다

왜: 주석 처리된 코드는 오래된 사본일 뿐이라 믿을 수 없는데도 읽는 사람의 시간을 계속 쓰게 한다. 진짜 이력은 버전 관리가 이미 보관한다.

좋은 예: 필요 없어진 코드는 주석 처리 대신 삭제하고, 다시 필요해지면 버전 관리 이력에서 되돌린다.

나쁜 예: "혹시 다시 쓸지 모른다"며 죽은 코드를 주석으로 쌓아 두고, 이후 누구도 지워도 되는지 판단하지 못한 채 파일이 군더더기로 자란다.

### 주석을 달기 전에 코드가 스스로 설명하게 만든다

왜: 주석은 코드와 함께 고쳐지지 않는 순간 낡은 문서가 된다. 코드 자체가 읽히면 낡을 것이 없다.

좋은 예:

```
IF 주문.총액 < 무료배송기준액:
    주문.배송비 = 기본배송비
```

나쁜 예:

```
# 총액이 5만 원 미만이면 배송비 3천 원을 붙인다
IF 주문.총액 < 50000:
    주문.배송비 = 3000
# 이름 없는 숫자를 주석으로 번역해 두면 정책이 바뀔 때 둘 다 고쳐야 한다
```

## 포맷·린트

### 포맷과 린트는 자동 도구에 맡긴다

왜: 자동 도구는 실수하지 않고 피로하지 않는다. 사람이 들여쓰기와 빈칸을 손으로 맞추는 시간은 더 가치 있는 일에 쓴다.

좋은 예: 저장 시 자동 포맷, 커밋 전 자동 검사가 갖춰져 있어 누가 편집하든 저장소가 같은 모양으로 유지된다.

나쁜 예: 독자마다 도구 설정이 달라 들여쓰기와 빈칸 차이가 매 편집마다 diff에 섞여 실제 변경을 가린다.

### 수동 포맷 논쟁을 하지 않는다

왜: 탭과 공백 같은 논쟁에는 정답이 없어 시간만 소모한다. 도구의 선택은 어느 누구의 취향과도 같으므로 감정 싸움이 될 여지가 없다.

좋은 예: 스타일 의견 차이가 생기면 "도구 설정이 어떻게 되어 있지?"로 종결한다.

나쁜 예: 리뷰 스레드에서 줄바꿈 위치를 두고 며칠씩 의견을 주고받는다.

### 구체적인 도구와 설정은 스택 문서가 정한다

왜: 무엇을 쓸지는 언어와 스택 생태계에 따라 달라지는 문제다. 이 문서는 원칙만 남겨 두면 스택이 확정된 뒤에도 다시 쓸 필요가 없다.

좋은 예: 스택 확정 시 [../stack/README.md](../stack/README.md)에 포맷터, 린터와 설정 파일 위치를 함께 명시한다.

나쁜 예: 스택도 정해지기 전에 특정 도구 이름을 표준 문서에 못 박아 둔다.

## 파일·모듈

### 한 파일은 한 가지 주된 책임만 가진다

왜: 파일이 여러 책임을 지면 무엇이 어디 있는지 찾기 어렵고 한 변경이 여러 이유로 같은 파일을 오가게 된다. 이 파일이 맡은 일을 하나로 말하지 못하면 나눈다.

좋은 예:

```
재고조회 함수는 재고조회 파일에, 재고차감 함수는 재고차감 파일에 들어 있다
```

나쁜 예:

```
회원, 주문, 결제 코드가 한 파일에 뒤섞여 있다
# 파일 이름은 "공통"인데 실제로는 아무것도 공통이 아니다
```
