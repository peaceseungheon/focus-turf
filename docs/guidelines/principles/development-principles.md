# 개발 원칙

이 문서는 이 저장소의 모든 코드 작업에 공통으로 적용되는 개발 원칙을 정의한다. 각 규칙은 한 줄 선언, 이유, 좋은 예와 나쁜 예로 구성하며, 스택이 확정되지 않았으므로 특정 도구 이름 없이 기술한다.

## 테스트

### 신규 기능의 핵심 로직에는 테스트를 작성한다 (강한 권장, 필수는 아님)

왜: 핵심 로직은 회귀 위험이 가장 큰 지점이고, 테스트가 이를 가장 적은 비용으로 지킨다. 강도는 명확히 `강한 권장`이므로 기본적으로 작성하되, 이후 논의로 예외를 두는 것까지는 막지 않는다.

좋은 예: 새 기능을 만들 때 `대표 입력 → 핵심 로직 실행 → 기댓값과 비교` 형태의 테스트를 같은 작업에 포함한다.

나쁜 예: "여유가 되면 테스트를 붙이자"라며 검증 없는 코드를 그대로 병합한다.

### 버그 수정에는 실패하는 재현 테스트를 먼저 작성한다 (필수)

왜: 재현 테스트가 없으면 그 버그가 정말 고쳐졌는지, 이후에 다시 깨지지 않는지 증명할 수 없다.

좋은 예: 버그를 받으면 가장 먼저 그 버그를 실패 상태로 만드는 재현 테스트를 작성한다.

나쁜 예: 증상을 손으로 한 번 확인한 뒤 재현 테스트 없이 수정 코드를 병합한다.

### 버그 수정의 "완료"는 `실패하는 재현 테스트 작성 → 통과 확인`으로 정의한다

왜: 작성자와 검토자가 같은 완료 기준을 공유해야 검수 논쟁이 사라진다. 재현 테스트가 통과하는 순간이 그 기준이 된다.

좋은 예: `재현 테스트 실패 확인 → 원인 수정 → 같은 테스트 통과 확인 → 완료 선언` 순서로 진행한다.

나쁜 예: "더는 에러가 안 보이니까"라는 근거로 완료를 선언한다.

## 에러 처리

### 실패를 조용히 삼키지 않는다

왜: 삼켜진 실패는 증상을 다른 곳에서 터뜨려 원인 찾기를 몇 배로 어렵게 만든다.

좋은 예: 처리하지 못할 오류는 로그와 함께 상위 계층으로 그대로 전파한다.

나쁜 예: 오류를 받아 놓고 빈 처리기로 무시하거나, 의미 없는 기본값으로 덮은 채 계속 진행한다.

### 에러는 경계(boundary)에서 처리한다

왜: 내부 로직은 오류를 값으로 다루고 시스템 가장자리에서만 사용자 응답과 로그로 변환하면 오류 흐름이 단순해진다.

좋은 예: 내부 함수는 오류를 반환값으로 넘기고, 최외곽 boundary에서 로그 기록과 사용자용 오류 응답으로 한 번에 변환한다.

나쁜 예: 깊은 내부 함수에서 오류를 문자열로 바꿔 화면 출력을 직접 호출한다.

### 로그에는 맥락을 포함한다

왜: 맥락 없는 로그는 어떤 요청, 어떤 데이터에서 문제가 생겼는지 알려 주지 못한다.

좋은 예: `작업 식별자 + 관련 입력 요약 + 오류 원인`을 한 줄에 함께 기록한다.

나쁜 예: "실패함" 같은 메시지만 남기고 무엇이 실패했는지는 남기지 않는다.

## 보안 기본

### 시크릿과 자격증명을 코드에 커밋하지 않는다

왜: 한 번 커밋된 비밀은 이력에서 지우기 어렵고, 즉시 무효화하고 교체해야 한다.

좋은 예: 비밀값은 환경 변수나 전용 비밀 저장소에서 읽고, 저장소에는 참조 방식만 남긴다.

나쁜 예: API 열쇠나 비밀번호를 코드 상수로 박아 넣고 커밋한다.

### 외부 입력은 검증을 통과해야만 신뢰한다 (외부 입력 검증)

왜: 사용자 입력과 외부 시스템 데이터는 형식, 범위, 의도 어느 곳에서든 기대를 벗어날 수 있다.

좋은 예: 외부 입력은 `스키마와 범위 검사를 통과한 경우에만` 내부 로직으로 전달한다.

나쁜 예: 외부에서 온 값을 검사 없이 질의 문자열이나 파일 경로에 그대로 이어 붙인다.

### 최소 권한 원칙을 따른다

왜: 권한이 클수록 사고나 침해 시 폭발 반경이 커진다. 필요한 만큼만 주면 피해도 그만큼 줄어든다.

좋은 예: 읽기만 필요한 작업에는 읽기 권한만, 필요한 기간에만 부여한다.

나쁜 예: 편의상 관리자 권한으로 모든 작업을 수행한다.

## 작업 단위

### 한 번에 하나의 논리적 변경만 한다

왜: 변경이 뭉쳐 있으면 원인 파악, 검토, 되돌리기가 모두 어려워진다.

좋은 예: 버그 수정과 리팩터링을 각각 독립된 작업으로 나눠 별도로 검증한다.

나쁜 예: 버그 수정, 이름 정리, 의존성 업그레이드를 한 덩어리로 제출한다.

### 코드를 고치기 전에 계획을 먼저 세운다

왜: 계획 없는 수정은 넓고 얕은 시도를 낳고, 되돌려야 할 변경의 양만 늘린다.

좋은 예: 고칠 지점과 원인 가설, 검증 방법을 짧게 적은 뒤 편집을 시작한다.

나쁜 예: 원인 가설 없이 눈에 보이는 코드를 순서대로 고쳐 본다.

## 지침 갱신 책임 (meta)

### 스택 확정이나 새 관행 도입 시 해당 지침 문서를 먼저 갱신한 후 작업한다

왜: 지침이 코드를 뒤따라가는 구조에서는 문서와 실제가 계속 어긋난다. 문서가 앞서야 기준으로 기능한다.

좋은 예: `새 저장 기술 도입 결정 → 관련 지침 항목 추가 → 도입 작업 착수` 순서로 진행한다.

나쁜 예: 지침은 그대로 두고 새 관행을 코드에만 먼저 적용한다.

### 지침에 없는 판단이 필요하면 임의로 결정하지 않고 사용자에게 질의/확인 요청을 한다

왜: 지침 밖의 판단을 스스로 내리면 프로젝트 방향과 어긋날 수 있고, 되돌리는 비용이 크다.

좋은 예: 근거와 선택지를 정리해 "A와 B 중 어느 쪽으로 갈까요?" 형태로 사용자에게 질의한다.

나쁜 예: 지침에 근거가 없는 선택을 조용히 임의로 결정하고 진행한다.
