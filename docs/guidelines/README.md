# 지침 인덱스

이 문서는 `docs/guidelines/` 아래 지침 문서 전체의 진입점이다. 무엇을 어디서 읽는지, 지침을 어떻게 갱신하는지, 해석이 충돌할 때 무엇이 우선인지를 한곳에서 안내한다.

## 1. 지침 체계 소개

이 지침 문서들은 저장소에서 일하는 에이전트와 사람이 공동으로 준수하는 기준이다. 누가 작업하든 같은 규칙을 참조할 때 결과가 일관되게 유지된다.

## 2. 문서 맵

| 분류 | 문서 | 용도 |
| --- | --- | --- |
| 원칙 | [설계 원칙](principles/design-principles.md) | 단일 책임, 개방-폐쇄 등 언어에 독립적인 핵심 설계 원칙을 정의 |
| 원칙 | [개발 원칙](principles/development-principles.md) | 테스트와 에러 처리 등 모든 코드 작업에 공통 적용되는 개발 원칙을 정의 |

## 3. 갱신 프로세스

- 규칙: 지침 변경도 일반 코드 변경과 동일하게 GitHub Flow PR 절차로 반영한다.
- 왜: 리뷰를 건너뛴 지침 변경은 준수 기준을 조용히 흔들고, 나중에 왜 바뀌었는지 추적할 수 없게 한다.

- 규칙: 지침을 바꾸는 PR에서는 AGENTS.md의 지침 맵이 실제 문서 목록과 일치하는지 확인한다.
- 왜: 맵이 실제와 어긋나면 독자와 에이전트가 존재하지 않는 지침을 찾아 헤맨다.

## 4. 충돌 우선순위

- 규칙: 구체적 문서(예: `stack/typescript.md`)가 일반 문서(`principles/`)보다 우선한다. 단, 설계 원칙 같은 핵심 원칙은 예외 없이 항상 적용한다.
- 왜: 구체적 문서는 일반 규칙을 해당 스택에 맞게 세부화한 것이지만, 핵심 원칙은 스택과 무관하게 지키는 바닥 기준이다.

- 규칙: 문서 간 해석이 충돌하면 임의로 정하지 않고 사용자에게 질의한다.
- 왜: 잘못된 해석은 하나의 작업에서 끝나지 않고 이후 모든 작업에 퍼진다.
